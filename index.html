Python Fundamentals

2.5 weeks

Topic 1: Variables, Data Types, Strings, Numbers

Days 1–2
▾

Why this matters: Every later Python concept — classes, functions, even FastAPI request bodies — is built on correctly understanding types. Skipping this shallow makes debugging type errors miserable later.

Resources
  • Official Python Tutorial — Ch. 3, An Informal Introduction
  • Corey Schafer — Python Beginner Tutorials playlist (watch: Strings, Numbers videos specifically)
  • Real Python — Basic Data Types (deeper reference, use when Corey's video isn't enough)

Do while learning: type every tutorial example yourself in a .py file, run it, break it on purpose (pass a string where a number's expected) and read the error message fully before fixing it.

▸ MINI-PROJECT Build a Unit Converter CLI — takes a value and converts between km↔miles, kg↔lbs, Celsius↔Fahrenheit, using only variables, strings, and arithmetic (no functions yet). Forces you to actually use string formatting (f-strings) and number handling for real.

PART 2

Building ArcadeGenesis, Module by Module

This section is the actual project build, broken into the exact modules from your synopsis, with what to build, in what order, and where to look things up.

MODULE 1

Component Library

2 weeks

Design, build order & metadata

▾

What you're building: ~30–40 standalone Phaser components split across two genres (grid-arcade, top-down shooter), each following a consistent interface.

Step 1 — Design the interface first, on paper.

Every component should expose:

interface GameComponent {
  id: string;
  initialize(scene, config): void;
  update(delta): void;
  destroy(): void;
}

Write this out and stick to it for every single component — consistency here is what makes the later Assembler possible at all.

Step 2 — Build components in this order (easiest → hardest):

  1. Grid genre: GridMovement, GrowingBody (Snake-style), FoodSpawner, WallBoundary, SelfCollision
  2. Top-down genre: TopDownMovement, PlayerShoot, EnemySpawner, EnemyChaseAI, HealthSystem, DamageOnCollision
  3. Shared/cross-genre: ScoreTracker, CameraFollow, PauseMenu, GameOverScreen, SoundManager

Build one at a time. Test each one alone in its own throwaway scene before moving to the next — don't build 5 components blind and debug them all at once.

Step 3 — Write metadata for each component as you finish it:

{
  "id": "top-down-movement",
  "genre": ["TopDownShooter"],
  "requires": ["Player"],
  "conflicts": ["GridMovement"],
  "alternatives": [],
  "priority": 10,
  "tags": ["movement"]
}

Keep all metadata in one components.json file — this file is your Component Library's data layer.

📎 REFERENCE Phaser 3 examples, browse by category whenever you're unsure how to implement a specific mechanic — search "top down movement," "sprite collision," "enemy follow player," etc.
MODULE 2

Manual Assembly Proof

4 days

Two hand-assembled games

▾

What you're building: Two complete small games, assembled entirely by hand, importing your Module 1 components directly — no AI, no automation yet.

Why this step can't be skipped: if two components fight when you wire them together manually, your metadata is wrong. Finding that out now costs you an afternoon. Finding it out after building the AI layer on top costs you a week of confused debugging.

  1. Step 1: Assemble a complete Snake-style game using only your grid-genre components.
  2. Step 2: Assemble a complete top-down shooter using only your top-down components.
  3. Step 3: Try combining one grid component with one top-down component on purpose (e.g. GridMovement + EnemyChaseAI) — confirm it actually breaks the way your conflicts metadata predicts. If it doesn't break the way you expect, your metadata is describing the wrong thing — fix it here.
MODULE 3

AI Game Planning Engine

1 week

Structured JSON plan from a natural-language prompt

▾

What you're building: An LLM call that takes a natural-language prompt and returns a structured JSON plan: { genre, components: [...], config: {...} }.

Resources
  • Groq API docs — chat completions
  • Groq API docs — JSON mode (if available for your model — check current docs, this changes)
  • Anthropic docs — Tool use / structured outputs
  • Prompt engineering guide — Anthropic
  1. Step 1: Write a system prompt that describes your component library (genre list, component IDs, what each does) and instructs the model to respond ONLY with JSON matching a fixed schema.
  2. Step 2: Send it 10+ genuinely different prompts ("a snake game where the snake speeds up over time," "top down shooter with 3 waves of enemies") and manually inspect each JSON response for correctness.
  3. Step 3: Add validation — if the JSON is malformed or references a component ID that doesn't exist in your library, catch it and either re-prompt or ask a clarifying question, don't silently fail.
💡 NOTE This reuses skills you already have from Coyot AI's Groq integration — the new part is strictly the "force valid JSON matching my schema" technique, not the API call itself.
MODULE 4

Compatibility Checker

4 days

Validating a component-ID list against metadata

▾

What you're building: A pure function: given a list of component IDs, walk your components.json metadata and return a validation result.

Step 1: Write check_compatibility(component_ids: list) -> dict that returns something like:

{
  "valid": false,
  "hard_conflicts": [["top-down-movement", "grid-movement"]],
  "soft_conflicts": [],
  "missing": []
}

Step 2: Test it against known-good combinations (should return valid) and known-bad ones (should catch the conflict) — write these as actual test cases, not manual checks, using Python's built-in unittest or pytest.

📎 RESOURCE Official pytest docs — Getting Started (worth learning properly now — you'll want real tests for this module specifically, since silent compatibility bugs are the worst kind to debug later)
MODULE 5

Recommendation Agent

1 week

Lookup substitution, then a plain-language layer

▾

What you're building: Activates only when Module 4 finds a hard conflict. Looks up alternatives in the metadata for the conflicting component, ranks them, and either auto-substitutes or returns options.

  1. Step 1: Simple version first — no AI, pure lookup: if X conflicts with Y, check X.alternatives, pick the first one that doesn't itself conflict with anything else in the plan.
  2. Step 2: Once the lookup version works reliably, add an LLM call on top that explains the substitution in plain language ("Flying doesn't work with platform movement, so I've swapped it for a Jetpack, which lets you fly with a fuel limit") — this is a nice-to-have polish layer, build it only after Step 1 works.
  3. Step 3: Test deliberately with prompts you know will conflict — this is your demo centerpiece, so test it more than any other module.
MODULE 6

Gameplay Assembler

4 days

Automating what you proved by hand

▾

What you're building: Takes a validated (post-compatibility-check) plan and generates the actual Phaser scene config — i.e., automates what you did by hand in Module 2.

  1. Step 1: Since you already proved manual assembly works in Module 2, this step is mostly "parameterize what you already wrote by hand" — replace hardcoded component choices with a loop over the plan's components list.
  2. Step 2: Test it by feeding it the exact same plans you used in Module 2 manually, confirm it produces an equivalent working game.
MODULE 7

FastAPI Backend + React Frontend

1 week

Wrapping Modules 3–6 behind one endpoint

▾

What you're building: Wraps Modules 3–6 behind one API endpoint, with a simple frontend.

Resources
  • Official React documentation — Quick Start
  • FastAPI — CORS docs (you'll need this since React and FastAPI run on different ports locally)
  1. Step 1: One endpoint: POST /generate-game — takes a prompt, runs Planner → Checker → Recommender → Assembler, returns the final game config JSON.
  2. Step 2: React frontend: a text input, a submit button, and a <div> where you mount the Phaser game canvas using the returned config.
MODULE 8

Project Memory

4 days

Sessions & messages so "make it faster" refines, not restarts

▾

What you're building: SQLite-backed storage of past prompts/plans per game session, so "make it faster" refines the existing plan instead of starting over.

  1. Step 1: Table: sessions(id, created_at), messages(session_id, prompt, resulting_plan_json, timestamp).
  2. Step 2: When a new prompt comes in for an existing session, include the last plan in the LLM context so it can modify rather than regenerate from scratch.
MODULE 9

Showcase Games + Evaluation

1 week

Polish, measure, document

▾
  1. Step 1: Build and polish 4 showcase games (2 grid, 2 top-down) through your actual pipeline — record short clips/screenshots.
  2. Step 2: Run 15–20 varied prompts through the full pipeline, log: did it produce a valid game? Did any conflicts get correctly caught and resolved? Compute your two headline metrics — generation success rate, conflict-resolution success rate.
  3. Step 3: Write the README with an architecture diagram (a simple boxes-and-arrows diagram is fine — draw it in Excalidraw, free and simple).
